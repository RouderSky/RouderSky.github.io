引用不是元素的副本

values[0] 返回的是 int&。把它绑定到 const int& 后，first 绑定的是缓冲区里的那个 int 对象，并没有复制出一个独立的值。

标准并没有规定 vector 必须按照两倍增长，也没有规定每次请求一定得到多大的容量。不同标准库实现可能采用不同的增长策略。

我们能够依赖的是：当现有容量不够时，vector 会重新分配一块能够容纳更多元素的连续空间，把原有元素移动或复制过去，再销毁旧缓冲区中的元素。

也正是在这一步，指向旧缓冲区的引用、指针和迭代器全部失效。

失效的不是“第几个元素”

人们有时把 values[0] 理解成“第 0 号位置”。更准确的理解是：

扩容后，元素虽然仍位于新 vector 的第 0 位，但底层地址已经改变。

因此下面这些值都可能在扩容后失效：

  • int& 或 const int&；
  • 指向元素的 int* 或 const int*；
  • vector<int>::iterator；
  • 通过 values.data() 得到的指针；
  • 范围 for 循环内部保存的迭代器。

它们共同依赖同一件事：元素仍然位于原来的缓冲区。

失效后不会触发一个可靠的运行时错误。引用仍能拿来写代码，指针仍能拿来解引用，迭代器仍能拿来执行 ++，只是行为已经不再受语言保证。

更不要通过固定写几个 push_back 来“记住”某台机器上的容量变化。更换编译器、编译选项、元素类型或 vector 的初始状态后，结论都可能改变。

范围 for 循环为什么也会出问题

范围 for 会先取得序列的起点和终点，再在循环过程中使用这些迭代器。它并不会在每一轮重新查询 vector 的全部状态。

一旦 push_back 触发扩容，循环正在使用的迭代器可能指向已经销毁的旧缓冲区。这个循环不但可能漏掉新加入的元素，还可能进入未定义行为。

capacity 大不等于元素还活着

clear() 会销毁所有元素，但通常不会释放已经分配的内存：

调用 clear() 后，capacity() 可能仍然是 3，但元素对象已经结束生命周期。继续使用 first 仍然是悬空引用。

erase()、shrink_to_fit()、赋值或移动 vector 等操作，也会以各自的规则影响引用和迭代器。判断时不能只看“内存有没有换一块”，还要看原来的元素对象是否仍然存在、是否仍由当前容器管理。

选择 std::deque、std::list 或别的容器也可以改变地址稳定性，但它们各自还有不同的失效规则和性能取舍。不要只因为“引用不会失效”就更换容器，先把访问模式、插入位置和遍历需求一起看清。

最后的检查点

  • 保存了 vector 元素的引用、指针或迭代器后，中间是否可能执行插入操作？
  • 这次插入是否可能触发扩容？
  • reserve 是否在所有保存引用的操作之前完成？
  • 是否把 capacity 误当成了元素数量？
  • 是否在范围 for 或持有迭代器的循环中改变了 vector 的大小？

vector 的连续内存带来了缓存友好和随机访问，也意味着扩容时必须整体搬走元素。只要记住引用和迭代器绑定的是某一块缓冲区，而不是抽象意义上的“第几个元素”，这些失效规则就不难判断了。
