本文最后更新于：2026年11月23日 晚上

C 风格字符串最容易被误会的地方，是它看起来像一种类型，实际上并不是。它是一套约定：从某个 char* 或 const char* 开始，一直读取到第一个空字符 '\0' 为止。std::string 则是一个管理自身字符缓冲区、同时保存长度的标准库类型。

两者可以互相配合，但不能把同一套操作习惯直接套过去。

标准库中接受 const char* 的函数，例如 strlen、strcpy、strcmp 和流输出，通常都不知道数组的真实长度。它们只能寻找空字符。若数组中不存在 '\0'，读取就会越过对象边界，行为未定义。

这个 std::string 明确保存了 11 个字符，其中包括中间的空字符。c_str() 会提供末尾空字符，方便旧接口使用，但 strlen 只数到第一个空字符，所以得到 5。

这并不是 std::string 的错误，而是两种数据模型不同：

  • std::string 同时知道起始位置和长度，可以保存嵌入的空字符；
  • C 风格字符串只有起始位置，长度由第一个空字符间接决定。

如果数据可能包含 '\0'，就不要用 strlen 推测长度，也不要把它交给只接受 C 风格字符串的接口。文件、网络和序列化代码中尤其容易遇到这种数据。

另一个常见问题是修改原字符串后继续使用旧指针：

追加内容可能触发重新分配，旧缓冲区随即失效。是否真的重新分配取决于当前容量和标准库实现，所以“这次还能打印”不能证明代码安全。

一个简单规则是：只在调用旧接口的短作用域内使用 c_str()，不要在多次修改 std::string 之后继续持有它。

返回 const char* 时要明确所有权

如果函数需要返回字符串，优先返回 std::string：

返回 const char* 时，调用者必须知道这块内存活多久：

  • 指向字符串字面量的指针具有静态存储期，可以长期使用；
  • 指向某个 std::string 内部缓冲区的指针只在满足条件时有效；
  • 指向局部字符数组的指针在函数返回后失效；
  • 指向动态分配数组的指针还涉及由谁释放。

接口只写 const char*，并没有表达这些所有权差异。若确实需要返回 C 风格字符串，应该在接口契约中说明生命周期，或者改用能表达所有权的类型。

现代 C++ 中，只读参数还可以考虑 std::string_view：

std::string_view 也只借用字符序列，不拥有内存。它避免了 const std::string& 与 const char* 之间的临时复制，但调用者仍要保证底层字符在视图使用期间有效。它也不是“更安全的 std::string”，而是另一种非拥有视图。

最后的检查点

  • 看到 char* 或 const char* 的 ==，先确认你想要比较地址还是内容。
  • 接受 const char* 的函数是否明确要求空字符结束？
  • 数据可能包含嵌入 '\0' 时，是否仍错误地用 strlen 计算长度？
  • c_str() 返回的指针是否跨越了原 std::string 的修改或销毁？
  • 返回裸 const char* 的接口，调用者是否知道内存由谁管理、能活多久？
  • 比较 size() 与有符号整数时，是否会发生无符号转换？

把这些边界分清之后，std::string 和旧接口并不冲突。关键不是完全拒绝 C 风格字符串，而是每次跨越边界时都明确：哪一边拥有内存，哪一边只是借用，以及长度和结束标记分别代表什么。
